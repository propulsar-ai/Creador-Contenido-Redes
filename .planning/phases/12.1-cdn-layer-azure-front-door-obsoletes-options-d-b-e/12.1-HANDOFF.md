## La evidencia dura (por qué AFD no es viable)

Hicimos **3 pruebas idénticas** contra Meta Graph API POST `/{IG_ACCOUNT}/media` con `media_type=STORIES`, desde el MISMO IP (dev de Felix), con el MISMO token válido, variando solo el `image_url`:

| Test | URL | Response | Archivo evidencia |
|------|-----|----------|---------------------|
| A | `https://cdn.propulsar.ai/posts/.../c91f69d9-....png` (custom domain AFD, DigiCert cert) | **400 / 9004** "Media could not be fetched" | `exec-captures/exec-14938.json` |
| B | `https://propulsarcontent-cybdebd3gkanevba.z01.azurefd.net/posts/...` (AFD default cert) | **400 / 9004** misma | `exec-captures/exec-14273.json` |
| C | `https://ideogram.ai/api/images/ephemeral/rL8pwEmrQy2RA0f9Ka-awg.png?exp=...` (Ideogram directo) | **200 `{"id":"17869171803666804"}`** | (test manual, container auto-expirado) |

Todos los 3 URLs servían 930KB PNG válido desde mi IP (verificado con HEAD + GET). El único bit que cambia entre Test C (pasa) y A/B (falla) es el **hostname del CDN**.

**Conclusión:** Meta Graph API `image_url` fetcher tiene un block/heurística explícita contra Azure Front Door hostnames. Probablemente Meta aplicó el mismo filter que aplica a `*.blob.core.windows.net` (el bloqueo 2026-04-17 que originó Phase 12.1) ahora también a AFD. Razón plausible: AFD comparte backend IP ranges o certificate chain patterns con Azure Blob que Meta clasifica como "cloud-provider subdomain" sospechoso.

**Wikipedia URL también falló en test previo desde dev IP con 9004**, pero por distinta razón (probablemente dimensiones o thumb URL redirect). Ese resultado me confundió al principio y me hizo dudar si era IP issue. El test C de hoy (Ideogram direct) prueba que NO es IP — es hostname.

## Plan para mañana — Phase 12.2 Cloudflare R2 Migration

### Objetivo

Migrar el re-host path de Azure Blob (`propulsarcontent.blob.core.windows.net`) a Cloudflare R2 con custom domain `cdn.propulsar.ai` (apuntando ahora a R2 en vez de AFD). Meta históricamente acepta Cloudflare domains. Unblock Phase 13 + restauran invariant Phase 4.

### Prerequisitos (que vos tenés que aportar mañana)

1. **Cuenta Cloudflare con R2 habilitado** — si ya tenés cuenta Cloudflare (es gratis crearla), solo tenés que ir a Cloudflare Dashboard → R2 → "Enable R2" (pide tarjeta para habilitar límites free tier, no cobra si no excedés: 10GB free storage + unlimited reads via CDN).
   - URL: https://dash.cloudflare.com/?to=/:account/r2
2. **R2 API credentials** — una vez habilitado R2, genero yo las credenciales S3-compatible vía API, guardo en Azure Key Vault `propulsar-prod-kv` (siguiendo el patrón existente con `godaddy-api-key`).
3. **Decisión:** ¿keep `cdn.propulsar.ai` name o cambiar a `img.propulsar.ai` / similar? **Mi voto: keep** — menos cambios. El CNAME actual en GoDaddy apunta a AFD; lo vamos a reapuntar a R2 cuando estemos listos para cortar.

### Plan de ejecución estimado (~3-4h total, secuencial)

**Wave 1: R2 setup** (~45min, paralelo)
- Vos: habilitar R2 en Cloudflare Dashboard (10min)
- Yo: crear bucket R2 `propulsar-content` vía API (usando Cloudflare API token que vos me pases); configurar lifecycle policy igual que Blob (retention 90 días)
- Yo: generar R2 API credentials (access key + secret) vía Cloudflare API; guardar en Key Vault como `cloudflare-r2-access-key`, `cloudflare-r2-secret-key`, `cloudflare-r2-account-id`
- Yo: setear env vars en Container App `propulsar-n8n` con referencias a los nuevos secrets
- Yo: configurar custom domain en R2 → `cdn.propulsar.ai` → R2 bucket (requires updating GoDaddy CNAME de AFD → R2 endpoint)

**Wave 2: workflow migration** (~60min)
- Yo: reescribir REHOST-01 (`📤 Subir a Azure Blob PUT`) → R2 PUT con S3-compatible signature (diferente de SAS). Node type cambia de HTTP Request a AWS S3 Put Object via `n8n-nodes-base.awsS3` con custom endpoint override.
- Yo: ajustar REHOST-06 (`🗂️ Collect blob_urls`) para emitir R2 public URL con `cdn.propulsar.ai` (no necesita rewrite en Code — R2 bucket config ya lo expone en custom domain)
- Yo: ajustar ERR-01 cleanup (`🗑️ Delete Azure Blob`) a R2 DELETE via S3 API
- Yo: mantener Options B (FB Story multipart — sigue necesario si FB `/photo_stories` URL fetcher es strict) y Option E (intra-cloud FB fetch desde R2 en lugar de Blob)
- Yo: **revertir los 5 Meta-facing nodes de Options D a `blob_urls[0].url`** (misma edición que hicimos en 3dcf574, ahora con R2 en lugar de AFD detrás)
- Yo: PUT deploy

**Wave 3: E2E verification** (~60-90min con tu SI en WA)
- Test 1: Story IG-only — yo disparo brief via fire-exec.mjs, vos SI en WA
- Si Meta devuelve 200 en Meta POST `/media` = R2 funciona → Test 2-5
- Test 2: Story IG+FB — multipart Option B con R2 source
- Test 3: Single-photo regression
- Test 4: Carrusel regression
- Test 5: Failure injection (rename un blob R2 mid-exec)

**Wave 4: cleanup + docs** (~30min)
- Borrar AFD profile + GoDaddy records AFD-related ($35/mo cost stop)
- Escribir 12.2-SUMMARY.md + cerrar 12.1 como FAILED con referencia
- Actualizar STATE.md + ROADMAP.md (Phase 12.1 → FAILED, Phase 12.2 → COMPLETE, Phase 13 → READY)

### Riesgos conocidos para Wave 3

- **R2 custom domain propagation:** al cambiar CNAME en GoDaddy de AFD → R2, hay 5-60min de DNS propagation. Mejor: usar R2 Public Access URL de Cloudflare (`pub-<hash>.r2.dev`) para la primera exec + cambiar a `cdn.propulsar.ai` después de validar que Meta acepta el R2 hostname subcomment.
- **Meta puede rechazar también `*.r2.dev`:** poco probable pero posible. Si pasa, el plan B es: Cloudflare R2 + custom domain DESDE EL DIA 1 (cdn.propulsar.ai). Hay precedente público de que Meta acepta custom domains sobre R2.
- **FB Story `/photo_stories` multipart**: mantener Option B — es defensive against URL fetcher bugs y ya funciona E2E.
- **Ideogram URL TTL 24h vs Meta fetcher timing**: irrelevante post-R2 si Meta acepta R2 URL, porque R2 URLs son permanentes.

### Fallback si R2 también falla (poco probable)

- Opción A: Amazon CloudFront + S3 — mayor trabajo, billing AWS (no queremos)
- Opción B: Volver a Options D/B/E permanente + aceptar Ideogram 24h TTL como feature (scheduling cap 22h) — Phase 13 puede seguir pero con esa restricción durable
- Opción C: Probar dominios alternativos: Netlify, Bunny.net, Fastly, etc.

Si Meta rechaza R2, al menos tenemos evidencia de 3 providers mainstream rechazados y podemos abrir Azure Support case con datos duros.
