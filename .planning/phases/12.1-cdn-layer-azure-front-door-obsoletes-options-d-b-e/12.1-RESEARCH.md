# Phase 12.1: CDN Layer — Azure Front Door obsoletes Options D/B/E - Research

**Researched:** 2026-04-23
**Domain:** CDN provisioning + n8n URL-builder retargeting + Meta Graph API compatibility
**Confidence:** HIGH (AFD path), MEDIUM (workflow blast radius — computed from local JSON grep, not yet re-deployed), LOW (permanence of Meta's domain block — single-tenant evidence only)

## Summary

Phase 12.1 restores the Phase 4 re-host invariant ("approved image = published image") that Meta broke on 2026-04-17 when it silently added `propulsarcontent.blob.core.windows.net` to its image-fetcher denylist. The fix is a CDN layer that Meta **will** fetch, sitting in front of the existing Azure Blob container so storage, SAS keys, and the Phase 4 `subworkflow-rehost-images.json` stay untouched. The only workflow change is swapping one URL builder and reverting five Meta-facing expressions that Options D/B/E currently point at Ideogram direct. Re-host sub-workflow, Azure Blob as canonical storage, SAS expiry, and `🗑️ Delete Azure Blob` cleanup all stay in place.

Azure Front Door Standard (**$35/mo base fee**) is the evidence-backed recommendation: same container, ~2h portal wizard, Microsoft-managed TLS cert, built-in Storage integration UI that preconfigures the origin host header and priority. Cloudflare R2 is a technically viable alternative but implies a storage swap (SAS → S3-compat creds, dual-write/re-upload of existing blobs, new env vars across n8n + subworkflow + Phase 4 nodes). R2's free tier covers the math (~$0.05/mo at current volume) but the migration cost (2-3 days + risk of regressions in Phase 4/5/6/7/8/9) outweighs the ~$35/mo savings for a single-tenant low-volume use case. Given Propulsar's bias toward "simple, durable systems over clever setups" (CLAUDE.md) and the existing Azure-native n8n runtime, AFD is the clear fit.

**Primary recommendation:** Use **Azure Front Door Standard tier**, integrated via the Storage account's built-in "Front Door and CDN" blade. Use the **default `*.z01.azurefd.net` endpoint hostname** for v1 (no DNS/custom domain work required to unblock Meta). Keep blob container anonymous-read disabled and configure AFD origin with SAS via rules-engine query-string append (or flip the container to public read for simplicity — documented tradeoff below). Revert Options D/B/E by re-pointing the 5 Meta-facing expressions from `final_image_url` (Ideogram direct) back to a CDN-built variant of `blob_urls[0].url`. Keep Option B multipart FB Story upload (it's durable and bypasses an FB-specific fetcher quirk separate from the domain block). Ship in ~3 plans: 12.1-01 AFD provisioning + smoke test; 12.1-02 workflow re-point + deploy; 12.1-03 E2E verification (same 5-exec pattern) + Options D/E cleanup.

## Architecture Patterns

### Recommended Deployment Topology

```
Client (Wizard)
    │
    │ POST brief
    ▼
n8n-azure (self-hosted on Azure VM)
    │
    ├─ Ideogram API → image bytes
    ├─ Phase 4 REHOST subworkflow → Azure Blob PUT (unchanged)
    │                              returns { blob_urls: [{ url: "https://propulsarcontent.blob.core.windows.net/..." }] }
    │
    ├─ URL builder (NEW / modified) → rewrites hostname to AFD endpoint
    │                                 returns { cdn_urls: [{ url: "https://propulsarcontent-xxx.z01.azurefd.net/..." }] }
    │                                 OR the blob_urls array is rewritten in place at REHOST-06
    │
    └─ Meta Graph API calls (IG Container, FB /photos, FB Carousel, IG Story Container, FB Story)
         ▼
       Meta fetcher → AFD PoP → (cache hit: serve) / (cache miss: fetch Azure Blob over private backbone, cache, serve)
```

### Pattern 1: URL rewriting at the earliest safe seam (Phase 4 REHOST-06 `🗂️ Collect blob_urls`)

**What:** Modify the REHOST sub-workflow's final aggregator node (`🗂️ Collect blob_urls`) to emit URLs with the AFD hostname instead of the raw Blob hostname.

**When to use:** Minimum-blast-radius choice. Downstream nodes (`🔗 Merge Rehost Output` and all Meta consumers) keep consuming `blob_urls[0].url` unchanged — the "canonical storage URL" contract is preserved by name; only the hostname differs.

**Example (pseudocode for REHOST-06 Code node):**
```javascript
// Phase 12.1: rewrite Azure Blob hostname → AFD CDN hostname
// Source: MS Learn — Use Azure Front Door with Azure Storage blobs
const cdnHost = $env.AZURE_CDN_HOST; // e.g. "propulsarcontent-xxx.z01.azurefd.net"
const rawBlobHost = `${$env.AZURE_STORAGE_ACCOUNT}.blob.core.windows.net`;

const items = $input.all();
const blob_urls = items
  .map(i => i.json)
  .sort((a, b) => a.slide_index - b.slide_index)
  .map(({ slide_index, blob_name, rehost_url }) => ({
    slide_index,
    blob_name,
    url: cdnHost
      ? rehost_url.replace(rawBlobHost, cdnHost)
      : rehost_url,  // fallback to Blob URL if env var missing (safe default)
  }));
return [{ json: { blob_urls } }];
```

**Rationale for this seam:**
- Phase 4 subworkflow already produces `rehost_url` — we rewrite hostname at the last mile.
- `🔗 Merge Rehost Output` and every `.blob_urls[0].url` consumer downstream need **zero changes** (same field, same shape).
- Env-var-gated fallback lets the workflow run safely if AFD is removed (degrades to current Options D/B/E behavior, not to a broken state).

### Pattern 2: Revert Options D/E — point Meta consumers back at `blob_urls[0].url`

**What:** Swap the 5 Meta-facing expressions that currently read `$('🎨 Ideogram image').item.json.image_url` (Ideogram direct) or `$json.final_image_url` (Option D/E band-aid) back to `$('🔗 Merge Rehost Output').item.json.blob_urls[0].url`.

**Nodes to revert (confirmed by grep on `n8n/workflow.json`):**
1. `📤 IG: Create Media Container` (line 1190 area — jsonBody `image_url`)
2. `🌐 FB: Publish Photo` (line 1361 — `url` field)
3. `📤 IG: Create Story Container` (line 1435 — jsonBody `image_url`)
4. `🧨 IG: Explode Carousel Slides` (line ~2389 — Code node, `image_urls` source)
5. `📤 FB: Upload Unpublished Photo` (line ~2220 — `image_url` in carousel FB fan-out)

**Keep as-is (FB Story chain):**
- `🛡️ Assert FB Story URL (no SAS)` — keep; strip logic is still correct defense-in-depth for CDN-fronted URLs (CDN URLs won't carry SAS after rewrite, but the strip is a no-op then, which is fine).
- `⬇️ FB: Fetch Image Bytes (Azure)` — keep; intra-cloud fetch from n8n-azure → AFD is still fine (or could revert to raw Blob, either works). Multipart upload to FB is durable.
- `📤 FB: Upload Story Photo Unpublished` — keep multipart/formBinaryData pattern. FB `/photo_stories` URL fetcher strictness (error 324 on Ideogram URL) is separate from the domain block; reverting this to `url=` would re-surface a pre-existing issue.

### Pattern 3: Immutable-blob cache headers (set at PUT time in REHOST-03)

**What:** Phase 4 REHOST-03 already uploads each blob with a UUID-based name (unique per image). Add `x-ms-blob-cache-control: public, max-age=31536000, immutable` header so AFD PoP caches aggressively.

**Why:** Meta may fetch the same image multiple times (IG Container, FB /photos, FB Story, retries). AFD cache hit eliminates origin round trips → ~zero egress cost even on Standard tier.

**Source:** Azure Blob REST API — `Put Blob` headers; AFD caching honors `Cache-Control`.

### Anti-Patterns to Avoid

- **Adding WAF / geo-filtering on the CDN:** Meta fetchers come from many IPs worldwide and don't identify themselves with a stable user-agent. Any restrictive WAF rule risks blocking Meta silently (same class of failure as Meta's own block of Azure Blob). Keep AFD open for GET.
- **Using Premium tier just to get Private Link:** $330/mo for security marginal over Standard+SAS. Private Link blocks direct blob access, but direct blob access is already effectively blocked by Meta's denylist, so the incremental benefit is low. Revisit only if a compliance requirement surfaces.
- **Rewriting URLs inside each Meta-consuming node instead of at REHOST-06:** Multiplies the edit surface (5+ nodes vs 1), makes rollback harder, and drifts from the "single canonical URL" Phase 4 invariant.
- **Switching storage providers mid-milestone:** v1.2 is 75% complete. Swapping to R2 now re-opens Phase 4 testing and blocks Phase 13. Defer R2 to post-v1.2 if cost becomes a driver.
- **Skipping the `AZURE_CDN_HOST` env var and hardcoding the AFD hostname:** Breaks reproducibility for Propulsar client projects (one of Propulsar's stated ICP goals) and makes staging/prod parity harder.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CDN layer for Azure Blob | nginx on an Azure VM acting as reverse proxy | Azure Front Door | AFD gives global PoP, managed TLS, caching, DDoS protection out-of-box; custom reverse proxy is one more thing to monitor and patch. AFD Standard at $35/mo is cheaper than any VM that would match its reliability. |
| TLS certificate management | Manually renew Let's Encrypt | AFD Azure-managed cert | Azure issues + auto-renews; no expiry alerts to configure. One less 2AM page. |
| Host header rewriting | Custom n8n HTTP middleware | AFD origin `originHostHeader` field | Built-in; Storage integration wizard sets it correctly by default. |
| URL signing / SAS injection | Build a signing Code node on each call | AFD Rules Engine query-string append OR public container | Both options are simpler than a per-call signer in n8n. |
| Image migration from Azure Blob to R2 | Write a dual-write tool | Don't migrate at all (stick with AFD path) | Migration risk outweighs savings for this volume. |

**Key insight:** AFD + existing Azure Blob is a **config** problem, not a **code** problem. Every hand-rolled alternative re-creates production concerns (TLS, caching, DDoS, global latency) that AFD includes in its $35/mo base fee.

## Common Pitfalls

### Pitfall 1: Meta still rejects the CDN URL because of generic bot-block behavior

**What goes wrong:** Even with CDN in place, Meta's fetcher could be rejected by a CDN-level bot-fight mode or by a WAF default rule set.

**Why it happens:** Meta fetchers don't identify with a stable user-agent, come from many IPs, and can trip "suspicious traffic" heuristics. Cloudflare's Bot Fight Mode specifically has caused this in production systems per Meta community posts (see Sources).

**How to avoid:**
- Do **NOT** enable WAF on the AFD profile in v1 (use Standard tier which has only custom WAF optional; leave disabled).
- Test with a real Meta Graph API call immediately after provisioning (see verification pattern below).
- If a false positive ever surfaces, add an explicit WAF exclusion for `AzureFrontDoor.FirstParty` service tag or loosen any custom rule; never add restrictive rules to start.

**Warning signs:** Meta returns code 9004 / subcode 2207052 / "Media could not be fetched" after deploy. Diagnosis: `curl -A "facebookexternalhit/1.1" <cdn_url>` from outside Azure should return 200 + image bytes.

### Pitfall 2: Container-level anonymous access vs SAS mismatch after CDN insertion

**What goes wrong:** Container is currently private + SAS tokens appended via `$env.AZURE_SAS_PARAMS`. AFD with SAS requires enabling `Use Query String` in cache behavior, otherwise all clients get one cached response (and SAS-less clients get served from cache despite having wrong SAS — security leak reversed direction too, SAS-bearing clients miss cache).

**Why it happens:** AFD's default cache-key strips query strings for hit-rate optimization.

**How to avoid:**
- **Option A (simpler):** Flip the `propulsarcontent` container to anonymous-read (**Blob** access level, not Container). Each blob is a UUID-named file; URL-unguessability is the only security layer (same posture as any public CDN-fronted static assets). Remove SAS injection entirely for Meta-facing URLs.
- **Option B (preserves SAS):** Enable AFD `Use Query String` behavior **and** append SAS via AFD Rules Engine so Meta fetcher doesn't need to carry SAS. Complex; higher blast radius; only needed if there's a compliance reason to keep the container private.

**Recommendation:** Option A. The blob names are UUIDs, content is public-by-intent (will be published to IG/FB anyway), and it removes three moving parts (SAS env var, rules engine, cache-key configuration).

**Warning signs:** After switching container anonymous-read, verify with `curl https://<account>.blob.core.windows.net/propulsarcontent/<blob_name>` (no SAS) returns 200; if 404/403, container ACL is still "Private."

### Pitfall 3: Forgetting to purge AFD cache after a blob is overwritten

**What goes wrong:** If a blob is ever overwritten under the same name (not current practice — REHOST uses UUIDs), AFD serves stale content until TTL expires.

**Why it happens:** AFD respects `Cache-Control`; `immutable` max-age=1yr means stale-for-1yr on overwrite.

**How to avoid:** Keep the UUID-per-image pattern (already in place). Do not re-use blob names. If ever needed, AFD portal has "Purge cache" action.

**Warning signs:** User reports Meta post shows "wrong image" on an iteration.

### Pitfall 4: Delete-blob cleanup hits AFD-cached content

**What goes wrong:** `🗑️ Delete Azure Blob` (ERR-01 cleanup) deletes the origin object, but AFD cached copy can still be served to Meta for TTL seconds.

**Why it happens:** CDN TTL is independent of origin lifecycle.

**How to avoid:** Cleanup is post-failure; Meta has already rejected the image at this point. AFD serving a stale copy to a retry of the same failed call is benign. No action required.

**Warning signs:** None expected; this is a theoretical edge case.

### Pitfall 5: Re-host sub-workflow can run before AFD endpoint exists (cold start)

**What goes wrong:** If the workflow deploys before AFD endpoint is provisioned, the URL builder emits an unreachable hostname.

**Why it happens:** Plan ordering dependency.

**How to avoid:** Stage provisioning first (Plan 12.1-01), verify with a curl smoke test, only then run the workflow-deploy plan (12.1-02) that reads `$env.AZURE_CDN_HOST`. The fallback in Pattern 1 (return raw blob URL if env missing) prevents a hard break in worst case — it degrades to "same as current" instead of crashing.

**Warning signs:** First post-deploy Meta call returns DNS NXDOMAIN or "Media could not be fetched."

### Pitfall 6: Meta's block might be broader than single-account

**What goes wrong:** STATE.md describes block as "domain-wide of `propulsarcontent.blob.core.windows.net`" but evidence (8 curl tests) is all against that one host. If Meta is blocking the `blob.core.windows.net` suffix globally, CDN-fronted Azure Blob will still be reachable **because the CDN hostname is `*.azurefd.net`**, which is the whole point. So this pitfall is **mitigated by design** — AFD path works in both interpretations of the block scope. This is a strong reason to choose AFD over "new Azure Blob account + custom DNS" (which only works under the narrower interpretation).

**How to avoid:** No action; AFD path is robust to either block scope.

**Warning signs:** Not applicable — AFD sidesteps the concern.

## Open Questions

1. **Is Meta's block account-specific (`propulsarcontent.blob.core.windows.net`) or suffix-wide (`*.blob.core.windows.net`)?**
   - What we know: STATE.md describes it as "domain-wide of `propulsarcontent.blob.core.windows.net`" — 8 curl tests during Plan 12-02 Task 2 v1 diagnostic confirmed rejection.
   - What's unclear: Whether Meta rejects **any** Azure Blob account or only ours.
   - Recommendation: **Don't test** — AFD path works under both interpretations. Testing requires spinning up a second Azure Blob account which is wasted effort since AFD already sidesteps the question.

2. **Will Meta begin blocking `*.azurefd.net` at some future date?**
   - What we know: No public statement from Meta. AFD is a massive shared CDN used by many customers including Microsoft's own properties; blocking it would have broad collateral damage.
   - What's unclear: Meta's policy trajectory.
   - Recommendation: Accept residual risk. Add monitoring (Phase 9 already has token alert pattern; could extend to "CDN reachability" check). Evidence cost of migration to another CDN if this ever happens is the same ~2h. Low urgency.

3. **Should we use a custom domain (e.g., `cdn.propulsar.ai`) instead of `*.azurefd.net`?**
   - What we know: Custom domain adds DNS CNAME work, domain validation, and AFD managed cert provisioning (~1h additional time). Brand benefit: Meta post sources show `cdn.propulsar.ai/...` not `propulsarcontent-xxx.z01.azurefd.net/...` (slightly more professional in any debugging UI).
   - What's unclear: Whether Propulsar owns `propulsar.ai` DNS and whether Felix wants this polish now or later.
   - Recommendation: **v1:** default `*.azurefd.net` — unblocks Meta in ~2h, zero DNS work. **v1.1 (follow-up, not Phase 12.1 scope):** add `cdn.propulsar.ai` custom domain as a polish PR. This is a trivial swap of the env var later.

4. **Should Option B (multipart FB Story) be reverted or kept?**
   - What we know: Option B was added because FB `/photo_stories` URL fetcher rejected Ideogram URLs (error 324). This failure mode is **separate** from the domain block — it's about FB's URL fetcher validating URL shape/domain rules. Whether FB will now accept an AFD CDN URL is uncertain.
   - What's unclear: Does FB `/photo_stories` URL fetcher accept `*.azurefd.net` hosts the same way IG `/media` does?
   - Recommendation: **Keep Option B multipart for FB Story.** Multipart upload bypasses FB URL fetcher entirely — durable and proven. Reverting introduces a new risk surface with no benefit (FB Story via multipart works today and has passed E2E exec 10647). Test plan: the verification pass should confirm FB Story still works post-CDN-migration.

5. **Will `blob_urls[0].url` still contain the SAS query string after hostname rewrite, and does that break anything?**
   - What we know: Phase 4 emits `https://propulsarcontent.blob.core.windows.net/propulsarcontent/<blob>?<SAS>`. Rewriting hostname yields `https://propulsarcontent-xxx.z01.azurefd.net/propulsarcontent/<blob>?<SAS>`. AFD can forward or strip query string per cache config.
   - What's unclear: Behavior interaction with the `🛡️ Assert FB Story URL (no SAS)` node that strips SAS (expects to find it).
   - Recommendation: Keep `🛡️ Assert FB Story URL` — strip logic is defensive and becomes a no-op if container flips to anonymous-read (no SAS ever appended at REHOST). Alternatively, remove `AZURE_SAS_PARAMS` from Phase 4 PUT if container is public. Resolve in Plan 12.1-02 as part of the URL-builder change.

### Key Findings

- **Azure Front Door Standard ($35/mo base, $0 routing rules, free first 100 custom domains) is the right fit** — native Storage integration blade, ~10 min to provision, managed TLS, sidesteps Meta's Blob domain block regardless of whether block is account-specific or suffix-wide.
- **Cloudflare R2 would cost ~$0.05/mo** but requires 2-3 days migration, SAS → S3 credential swap, custom domain (r2.dev is dev-only per Cloudflare docs), and rewrites Phase 4. Not worth it mid-milestone.
- **Minimum-blast-radius rewrite is at REHOST-06 `🗂️ Collect blob_urls`** — rewrite hostname from `<account>.blob.core.windows.net` to `$env.AZURE_CDN_HOST`; downstream consumers see the same `blob_urls[0].url` field shape with only the hostname swapped.
- **5 Meta-facing nodes need to revert from Option D** back to `$('🔗 Merge Rehost Output').item.json.blob_urls[0].url`: IG Create Media Container, FB Publish Photo, IG Create Story Container, IG Explode Carousel Slides, FB Upload Unpublished Photo.
- **Keep Option B multipart for FB Story** — it's durable and bypasses an FB-URL-fetcher strictness separate from the domain block. Reverting introduces risk for no benefit.
- **Default `*.azurefd.net` endpoint hostname is sufficient for v1** — no DNS/custom domain work required. Custom `cdn.propulsar.ai` is a later polish PR.
- **Recommend flipping container to anonymous-read (Blob level)** to eliminate SAS+cache-key complexity. Blob names are UUIDs; security posture matches industry CDN-fronted static asset pattern.
- **Suggested plan breakdown: 3 plans, ~4-5h total, 0 net node count change** — 12.1-01 AFD provisioning + smoke test, 12.1-02 workflow re-point + deploy, 12.1-03 E2E verification + D/E cleanup.
