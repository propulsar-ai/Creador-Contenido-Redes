# Phase 12.3: Supabase to Azure Postgres Migration - Research

**Researched:** 2026-08-01
**Domain:** n8n workflow rewiring (HTTP/PostgREST → native Postgres node) + Azure PostgreSQL Flexible Server provisioning
**Confidence:** HIGH (every finding below is verified live against this exact Azure subscription and this exact n8n instance — not generic docs)

## Summary

The Supabase project backing `content_sessions` (`wcjyayeyamyhrjqujhyv.supabase.co`) is permanently deleted, breaking session persistence for all three post formats (single/carousel/Story) in `Propulsar — Content Engine v3` (n8n workflow id `Qql7mvYRxKBsPZ5t`). Four HTTP Request nodes hit PostgREST endpoints on that dead host: 3 writes (`💾 Guardar sesión Supabase`, `💾 Guardar sesión Supabase (Carousel)`, `💾 Guardar sesión Supabase (Story)`) and 1 read (`🔍 Recuperar sesión Supabase`, the approval-webhook session-recovery lookup keyed by phone number). No other file in this repo (`wizard/run.js`, `scripts/`, `SETUP.md` sections outside FASE 4) and no other n8n workflow on this instance (checked `Asistente de Redes - Agente IA (IG/FB)` and the `Re-host Images to Azure Blob` sub-workflow, both zero Supabase references) touch this table — the blast radius is exactly these 4 nodes plus 3 downstream "re-attach" Set nodes that read fields off the Supabase HTTP response shape.

**The good news:** Propulsar already runs a shared Azure Database for PostgreSQL Flexible Server (`propulsar-db`, PG15, Burstable B1ms, `propulsar-production` resource group, North Europe) that **n8n itself uses as its own operational database** (`DB_POSTGRESDB_HOST=propulsar-db.postgres.database.azure.com` is already wired on the `propulsar-n8n` Container App). This is proof-positive that the Container App can already reach this server over the network (firewall rule `AllowAzureServices 0.0.0.0` is in place) — no new provisioning, no new firewall rule, no new server needed. Two other n8n workflows on this exact instance (`GHL Sync: Contacto -> Prospecto`, `Propulsar - Unificar Contacto`) already use the native `n8n-nodes-base.postgres` node (typeVersion 2.5/2.6) with `executeQuery` + parameterized `$1,$2...` SQL against a dedicated database (`propulsar_crm`) on this same server, via an n8n-native `postgres`-type credential — this is a working, live template to copy, not a hypothesis.

**Primary recommendation:** Create one new database (`content_engine`) on the existing `propulsar-db` server via `az postgres flexible-server db create` (no psql/network access needed — it's an ARM control-plane call). Reuse the existing admin login (`propulsaradmin`, password already in Key Vault as `db-postgresdb-password`, already wired to this Container App) for a new n8n credential named `Postgres - content_engine`, created either via the n8n public API (`POST /api/v1/credentials` — schema-discovery endpoint confirmed working live, strong evidence POST also works) or, as a fallback checkpoint, by hand in the n8n UI. Replace the 4 HTTP Request nodes' `type`/`parameters`/`credentials` with `n8n-nodes-base.postgres` + `executeQuery`, keeping node `id` and display `name` unchanged (connections are keyed by name, not id — no connections-graph edits needed). Add one new guard node after the recovery read to preserve the "no pending session found → hard error" behavior that PostgREST's 406-on-empty-or-multiple gave for free (the native Postgres node returns `[]` silently instead of throwing — this is the single biggest behavioral gap to close).

**1. `save-session-supabase` (single-post write, ~line 414-459) — no `retryOnFail` today.**

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Talking to Postgres from n8n | A raw `n8n-nodes-base.httpRequest` node hitting some REST layer, or a Code node with a hand-rolled `pg` client | `n8n-nodes-base.postgres` node, `executeQuery` operation | Native node handles connection pooling, SSL, parameter binding, and array/type coercion; Code node sandbox in this instance historically blocks arbitrary `require()` (though `NODE_FUNCTION_ALLOW_BUILTIN=https,http,url,crypto` is set on this Container App — `pg` still wouldn't be available, it's not a Node builtin) |

## Common Pitfalls

### Pitfall 1: Empty-result behavior silently changes (the most important one)

**What goes wrong:** The old `🔍 Recuperar sesión Supabase` node relied on PostgREST's `Accept: application/vnd.pgrst.object+json` header, which returns **HTTP 406** when the query matches 0 or >1 rows — causing the n8n HTTP node to throw and halt the execution with a clear error (per that node's own `notes` field: "Empty result → 406 → execution fails with clear error"). The native Postgres node's `executeQuery` with 0 matching rows returns an **empty array `[]`, not an error** — downstream nodes simply receive zero items and n8n quietly stops processing that branch (no thrown error, no clear failure signal in the execution log).

**Why it happens:** PostgREST and the raw Postgres wire protocol have fundamentally different "no rows" semantics; the old design accidentally depended on a PostgREST-specific HTTP status code as its error-signaling mechanism.

**How to avoid:** Add an explicit guard node immediately after `retrieve-session` (mirroring the existing `🛡️ Assert FB Story URL (no SAS)` Code-node pattern already in this workflow) that throws a clear `Error('...')` when the item array is empty. `ORDER BY ... LIMIT 1` already prevents the ">1 row" case (the known "2 pending posts same approver collides" bug is unaffected by this migration either way — same limitation, different technical cause).

**Warning signs:** If this guard is skipped, a WhatsApp "SI" reply from a user with no pending session will silently produce zero workflow output instead of a diagnosable error — much harder to debug than the old 406.

**Confidence:** MEDIUM — corroborated by multiple n8n community reports (not official docs) that `executeQuery` returns `[]`/empty result sets rather than throwing on no-match; the planner's first live-fire test in this phase's E2E step will definitively confirm this instance's exact behavior at zero extra cost (it's part of the planned verification anyway).

### Pitfall 2: Binding a JS array to a JSONB column requires an explicit cast

**What goes wrong:** If the planner chooses `JSONB` instead of `TEXT[]` for `platforms`/`image_urls`, passing a raw JS array through `queryReplacement` (e.g. `$json.platforms`) to a `$N` placeholder bound to a `jsonb` column fails or silently miscoerces, because the `pg` driver doesn't know the target column type ahead of binding.

**How to avoid:** This research recommends `TEXT[]` for both columns specifically to sidestep this — the pg driver serializes JS arrays to Postgres arrays natively with zero casting. If JSONB is chosen anyway (e.g., future-proofing for nested objects), cast explicitly in SQL (`$1::jsonb`) and `JSON.stringify()` the value in the n8n expression.

**Confidence:** MEDIUM (community-reported n8n/pg-driver pattern) — moot if `TEXT[]` is used as recommended.

### Pitfall 3: Deploy must patch around the known AOAI drift, not full-file PUT

**What goes wrong:** A blind `PUT` of the whole `n8n/workflow.json` would revert production's out-of-band Azure OpenAI migration on `openai-text`/`openai-carousel`/`parse-carousel`/`parse-content` (see STATE.md Open Items) — this exact mistake was already caught and avoided once, in Plan 12.2-02.

**How to avoid:** Fetch remote workflow JSON, diff by node id against the repo's committed baseline, and patch only this phase's 4-5 target nodes into the remote JSON before `PUT` — the established pattern from `12.2-02-DEPLOY.md`.

**Confidence:** HIGH — directly observed and documented in this project's own history, not inferred.

### Pitfall 4: n8n public API credential creation is plausible but not proven

**What goes wrong:** The plan might assume `POST /api/v1/credentials` definitely works and build a fully-scripted deploy around it, only to discover at execution time that credential creation (unlike schema-discovery/list/get) is blocked or behaves differently.

**How to avoid:** Treat the API path as "try first" with the n8n UI as an explicit fallback checkpoint in the plan, not a hard dependency. See Open Questions.

**Confidence:** LOW-MEDIUM — see below.

## Open Questions

1. **Does `POST /api/v1/credentials` actually succeed on this n8n instance?**
   - What we know: `GET /api/v1/credentials` (list), `GET /api/v1/credentials/{id}` (metadata, no secret), and `GET /api/v1/credentials/schema/{type}` all return 200 live on this instance — official n8n docs group Credential as a standard REST resource with full CRUD.
   - What's unclear: No actual `POST` was attempted during this research (avoided creating an untracked side effect against production credentials during a research-only session).
   - Recommendation: Plan should attempt the API-based creation as Task 1's first step, with a clear, low-friction fallback (manual UI credential creation, ~2 min) if it 403s/404s/500s. Do not architect the whole plan around the API path being guaranteed.

2. **Reuse `propulsaradmin` vs. a dedicated least-privilege role?**
   - What we know: Reuse is simpler, free, and matches how n8n's own core DB connection already works on this exact Container App.
   - What's unclear: Whether the user has an explicit preference for tighter credential isolation given this table will eventually (future, out-of-scope project) grow into a GUI-facing history panel per `CONTENT-STUDIO-GUI-SEED.md`.
   - Recommendation: Default to reuse (tiebreaker rule); note the dedicated-role path as a 10-minute upgrade if the user wants it later — it does not block this phase either way.

3. **Should `platforms`/`image_urls` be `TEXT[]` or `JSONB`?**
   - What we know: Original Supabase schema used `TEXT[]` for `platforms`. `image_urls`'s original type is unknown (added via an undocumented ALTER during Phase 7, never captured in SETUP.md).
   - Recommendation: `TEXT[]` for both, for the casting-simplicity reasons in Pitfall 2. Low-risk either way since this is a brand-new table with no migrated data.
