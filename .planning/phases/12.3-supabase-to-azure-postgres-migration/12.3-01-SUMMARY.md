## Decisions Made
- **pg npm driver instead of `az postgres flexible-server execute`** — the `rdbms-connect` Azure CLI extension fails to install in this environment (pip/setuptools `BackendUnavailable` error inside the Azure CLI's embedded Python), and no `psql` binary exists on this machine. The project's own `pg` package (already in `node_modules`, the same driver n8n's native Postgres node uses under the hood) was used via a scratch Node.js script with identical connection parameters (`host`, `database`, `user`, `password` from Key Vault, `port`, `ssl: { rejectUnauthorized: false }` matching n8n's own `DB_POSTGRESDB_SSL_REJECT_UNAUTHORIZED=false` setting for this server). Same outcome, different tool.
- **API-first credential creation succeeded, no checkpoint needed** — `POST /api/v1/credentials` returned HTTP 200 with a valid credential id on the very first attempt. Per the plan's explicit branching logic, Task 3 (the manual-UI fallback checkpoint) was correctly skipped.
- **Reused `propulsaradmin` admin login** — matches n8n's own core DB connection on the same Container App, follows the Propulsar tiebreaker rule (simplest / cheapest / already-used-elsewhere). A dedicated least-privilege role remains a documented future upgrade path (RESEARCH Open Question #2), not required for this phase.

- **Verification:** DDL executed successfully, all 20 columns confirmed via `INSERT ... RETURNING *`, recovery SELECT returned exactly 1 row, DELETE + post-delete confirmation returned 0 rows — identical evidence to what the plan's specified tool would have produced.
