## Deviations

**1. [Rule 3 - Blocking] Trimmed `settings` object for the PUT payload**
- **Found during:** Task 1, first PUT attempt
- **Issue:** `400 request/body/settings must NOT have additional properties` — remote's GET response (and the repo's stored `n8n/workflow.json`) both include `availableInMCP` and `binaryMode` in `settings`, but this n8n instance's PUT schema rejects them as unknown additional properties.
- **Fix:** Trimmed the PUT payload's `settings` to the 3 accepted keys (`executionOrder`, `saveManualExecutions`, `callerPolicy`) before retrying. Values for all 3 kept identical to remote (`v1`, `true`, `workflowsFromSameOwner`).
- **Files modified:** None (deploy-script-only change, not a repo file edit — `n8n/workflow.json` in the repo still stores the full 5-key settings object as returned by GET, matching prior plans' convention).
- **Verification:** Retried PUT returned `200`; re-GET confirms workflow deployed correctly with `active: true` preserved.
- **Note for future deploys:** any future full-file or patch-based PUT to this n8n instance should proactively strip `availableInMCP`/`binaryMode` from `settings` before sending, or use a `settings: {executionOrder, saveManualExecutions, callerPolicy}` literal rather than passing through GET's response verbatim.
