## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Trimmed n8n PUT `settings` payload to 3 accepted keys**
- **Found during:** Task 1, first PUT attempt
- **Issue:** `400 request/body/settings must NOT have additional properties` — remote GET returns 5 settings keys (`executionOrder`, `saveManualExecutions`, `callerPolicy`, `availableInMCP`, `binaryMode`), but the PUT schema only accepts the first 3.
- **Fix:** Sent `settings: {executionOrder, saveManualExecutions, callerPolicy}` only, values unchanged from remote.
- **Files modified:** None (deploy-script-only; `n8n/workflow.json` in the repo still stores the full 5-key object as returned by GET, consistent with prior plans).
- **Verification:** Retried PUT returned 200; re-GET confirmed `active: true` preserved and workflow deployed correctly.
- **Committed in:** `13e5fff` (documented in `12.3-03-DEPLOY.md`)

## Issues Encountered

- **First live fire (exec `1787106`) — WhatsApp messages "accepted" by YCloud but failed delivery (`errorCode 131047`, 24h customer-service window closed on the approval number).** This is a WhatsApp Business API policy constraint entirely unrelated to the Supabase→Postgres migration or this plan's deploy — the underlying pipeline (including the newly-deployed Postgres INSERT) had already succeeded before this point. Diagnosed via a direct `GET /v2/whatsapp/messages/{id}` call to YCloud (never trust the synchronous "accepted" the send call returns). Resolved when the user sent an inbound message to the business number, reopening the 24h window; the re-fire (exec `1787184`) delivered both messages cleanly (confirmed `status: "delivered"` via the same direct-GET method) and the user received and replied NO.
