`rehost-service/package.json`: minimal, `express` only (no `multer` — use raw PUT with a binary body-parser, mirroring the existing Azure Blob PUT-with-binary-body pattern more closely per RESEARCH installation note). Add a `start` script (`node server.js`).

`rehost-service/server.js` — three routes, matching the exact auth split RESEARCH Pitfall 6 demands:
- `PUT /files/*` — wildcard captures the full nested path (e.g. `2026/07/31/<uuid>.png`, matching the existing `build-blob-name` Code node's `YYYY/MM/DD/<uuid>.<ext>` shape in `n8n/subworkflow-rehost-images.json` verbatim — no reshaping needed on the n8n side). Requires header `X-Api-Key` matching `process.env.REHOST_API_KEY`; 401 if missing/wrong. Reads the raw request body as a buffer (`express.raw({ type: '*/*', limit: '25mb' })`), writes it to disk under a base directory (e.g. `/data/files/<path>`), creating intermediate directories as needed (`fs.mkdirSync(dir, { recursive: true })`). Returns `200 { path, bytes }` on success.
- `GET /files/*` — **fully public, zero auth check** (Meta's fetcher cannot send custom headers — RESEARCH Pitfall 6 is the one failure mode this route must never reproduce). Streams the file back with a `Content-Type` header derived from extension (`.png`→`image/png`, `.jpg`/`.jpeg`→`image/jpeg`, `.webp`→`image/webp`, default `application/octet-stream`). 404 if the file doesn't exist (not a crash).
- `DELETE /files/*` — same `X-Api-Key` auth as PUT. Deletes the file if present, returns `200 { deleted: true }`; returns `200 { deleted: false }` (NOT an error) if the file was already absent — mirrors the ERR-01 cleanup path's fail-open expectations (delete-then-verify-gone, not delete-must-exist).
- Add a `GET /health` route (no auth) returning `200 {"status":"ok"}` for a cheap liveness check independent of any specific file.

Do not add multer, do not add any DB — this is a stateless file-serving API over a mounted directory, exactly as RESEARCH's Alternatives Considered table recommends over MinIO for this phase's scope.

`rehost-service/Dockerfile` — single-stage, mirror the proven pattern from `../propulsar-atiende/Dockerfile` (a sibling repo at `c:/Felix/Automatizaciones/Propulsar/Proyectos/propulsar-atiende`, NOT a subfolder of this repo — comment explaining WHY: EasyPanel's Dockerfile build type always builds the file literally named `Dockerfile` at the build context root, confirmed in `deploy-vps-demo.md` §3):
```dockerfile
FROM node:20-slim
WORKDIR /app
COPY package.json ./
RUN npm install --omit=dev
COPY server.js ./
EXPOSE 8000
ENV PORT=8000
CMD ["node", "server.js"]
```
`server.js` must read the listen port from `process.env.PORT || 8000` (VPS backend port convention per `deploy-vps-demo.md` §2, port 8000 for backends).

Commit this task's 3 files with a `feat(12.2-01):` commit and push to `origin/main` — EasyPanel's `services.app.updateSourceGit` (Task 2) builds from the pushed remote, not the local working tree (RESEARCH/deploy-vps-demo.md §1 explicit warning).
  </action>
