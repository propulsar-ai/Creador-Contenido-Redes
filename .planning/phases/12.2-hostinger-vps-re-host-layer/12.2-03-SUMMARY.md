## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] No n8n public REST endpoint exists to directly execute a workflow**
- **Found during:** Task 1, before writing any test code
- **Issue:** The plan's Task 1 offered "via n8n's execute-workflow REST endpoint" as one option. Live testing (`POST /api/v1/workflows/{id}/run`) confirmed this returns `405 {"message":"POST method not allowed"}` — no such endpoint exists in this n8n instance's public API.
- **Fix:** Used the plan's own explicitly-offered fallback ("or by feeding it through a minimal main-workflow test path"), implemented as a disposable harness workflow (`Webhook -> Flatten Body -> Execute Workflow -> real sub-workflow`) rather than modifying the real main workflow — safer, since it never touches production's main workflow at all.
- **Files modified:** none permanent (harness workflow lived only in n8n, deleted at cleanup)
- **Verification:** harness successfully invoked the real sub-workflow twice (Execution A, B), confirmed via matching execution ids in `/api/v1/executions`
- **Committed in:** `c9520f7` (Task 1 commit, documents the finding in the script's header comment)

**2. [Rule 3 - Blocking] The real approval-webhook path has no safe stopping point before Meta-facing nodes**
- **Found during:** Task 1, while evaluating the "minimal main-workflow test path" option
- **Issue:** Reading the live main workflow's `🔧 Prep Re-host Input` node revealed the re-host sub-workflow call happens *after* WhatsApp SI approval (not before, as might be assumed from a linear read of the pipeline), and `🔗 Merge Rehost Output` connects directly into the format-branch leading straight into the 5 Meta-facing container-creation nodes — approving a real brief via WhatsApp would risk firing real Meta calls mid-test.
- **Fix:** The harness workflow (see deviation 1) sidesteps this entirely by calling the sub-workflow directly, never touching the main workflow's approval/publish chain.
- **Files modified:** none
- **Verification:** Harness executions never touched the main workflow (`Qql7mvYRxKBsPZ5t`) at all — confirmed by execution records showing only the harness and sub-workflow workflow ids
- **Committed in:** `c9520f7` (Task 1 commit)

**3. [Rule 3 - Blocking] Local `.env`'s `N8N_API_KEY` still expired (pre-existing, flagged in Plan 02)**
- **Found during:** Task 1 setup
- **Issue:** Same expired key noted in Plan 12.2-02's Open Items — not yet rotated.
