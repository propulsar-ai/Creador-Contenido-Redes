## Persistent volume — Task 2 Step 5 (real finding, escalated below)

Extensive investigation (~50 candidate procedure names tried against `services.app.*` and a few alternate namespaces) found **no working EasyPanel tRPC procedure to set a mount on an app-type service.** `inspectService` shows a `"mounts": []` field but every write attempt (`updateMounts`, `setMountPoints`, `createVolumeMount`, `updateResources` with a `mounts` key, etc.) either 404'd (`{"error":"Not found"}` — route doesn't exist) or silently accepted-and-dropped the field (confirmed via `updateResources`, which returns `{}` but does not persist an unknown `mounts` key, matching this instance's documented "accepts any field without validating" gotcha).

**Fallback used (per plan instruction):** `hostShell` WebSocket → direct `docker service update --mount-add type=bind,source=/etc/easypanel/projects/propulsar-atiende-demo/rehost-service/data,target=/data propulsar-atiende-demo_rehost-service`. This is real, live infrastructure (this VPS runs Docker **Swarm**, confirmed via `docker service ls`) and the mount **does** attach and serve correctly — verified live: PUT → GET (same bytes) both worked with the mount attached.

**Real gap found (escalating per plan's explicit instruction, not just noting it here):** `services.app.restartService` (the EasyPanel tRPC procedure) **regenerates the container spec from EasyPanel's own stored config** — which has no knowledge of our manually-added Docker-level mount — and **silently drops it** on any restart triggered through the panel/API. Live proof:

1. PUT `2026/07/31/persist-test.png` (mount attached) → GET same URL → 200, bytes match.
2. `services.app.restartService` called (the officially-documented way to apply an env change / restart, per `deploy-vps-demo.md`).
3. GET same URL → **404**. `docker service inspect ... ContainerSpec.Mounts` → `null` (mount gone from the live spec).
4. **Host-side data was NOT lost** — `find /etc/easypanel/projects/.../rehost-service/data` on the host still showed the file. The gap is that the *container* loses its attachment to that host directory on any EasyPanel-triggered restart/redeploy, not that the underlying bytes are destroyed.
5. Mount manually reapplied (`docker service update --mount-add ...` again) → GET → 200 again, same bytes → confirms the recovery path also works.

**Consequence:** as of this plan's close, `rehost-service`'s persistent volume is **live and working today**, but **any future `restartService`/`deployService` call against this service (including a routine env-var change or a future code redeploy) will silently make all previously-uploaded files 404 until someone manually re-runs the `docker service update --mount-add` hostShell command.** No EasyPanel-native mechanism was found to make this durable through the panel's own restart/redeploy path. Data is not deleted, only temporarily disconnected — but for a live Meta-facing image host, a `404` during that window is operationally equivalent to an outage for whatever image was mid-flight.

**Escalated to the user directly** (this is a real, live durability gap in production infra, not resolved by this plan) — see `12.2-01-SUMMARY.md` → Deviations, and flagged again at the end of this session's final response. Recommended before Plan 03 closes the phase: either (a) accept this as a documented operational runbook step (re-run the mount command after any future restart/redeploy of this specific service), or (b) a follow-up session investigates via the actual EasyPanel web UI (requires the panel's email/password login, not currently stored anywhere accessible) to find the real "Mounts" UI flow and its underlying API call.
