# Phase 12.2: Hostinger VPS Re-host Layer - Research

**Researched:** 2026-07-31
**Domain:** Self-hosted file upload/serve/delete HTTP microservice on an EasyPanel-managed VPS, consumed by n8n as a durable Meta-reachable image host, replacing Azure Blob as the re-host backend.
**Confidence:** HIGH (empirically re-verified live against the actual EasyPanel instance and actual repo state during this research session, not just documentation review)

## Summary

Phase 12.1 (Azure Front Door) failed because Meta's Graph API `image_url` fetcher rejects all Azure Front Door hostnames. A smoke test on 2026-07-31 proved Meta accepts images served from Propulsar's existing Hostinger VPS via its EasyPanel wildcard domain (`*.bacu5y.easypanel.host`), using a throwaway `httpbin` container. This phase must turn that smoke test into a real, durable re-host backend: a small HTTP service with upload (PUT), serve (GET), and delete (DELETE) semantics, deployed as a new service inside the existing `propulsar-atiende-demo` EasyPanel project (the 3-project plan cap is confirmed still exactly full: `n8n`, `evolution-api`, `propulsar-atiende-demo` — verified live during this research, no new top-level project is possible), then rewiring the n8n sub-workflow and 5 Meta-facing nodes to point at it instead of Azure Blob.

The critical correction this research surfaces: the smoke-test doc's own suggested candidate, `halverneus/static-file-server`, **does not support upload or delete at all** — it is read-only (verified against its README/GitHub; only serves pre-existing files, no PUT/DELETE, no write-capable env var). That candidate must be dropped. The only viable paths are (a) a small custom HTTP API (Node/Express or Python/FastAPI) deployed via EasyPanel's git+Dockerfile flow, mirroring the exact working Dockerfile-with-runtime-mode pattern already proven for `propulsar-atiende` on this same VPS, or (b) MinIO (S3-compatible) via n8n's native S3 credential type, which does support a custom endpoint override — verified as an official, documented n8n feature — but carries a real, currently-unresolved signature-compatibility GitHub issue for some MinIO configurations, plus meaningfully more operational surface (auth model change from simple header/query auth to AWS SigV4, bucket policies for public read) than the current codebase's established HTTP-Request-node pattern.

**Primary recommendation:** Build a small custom Node/Express (or Python/FastAPI) upload/serve/delete HTTP API, deployed as a new sibling service inside `propulsar-atiende-demo` via `services.app.createService` + `services.app.updateSourceGit` (git+Dockerfile, PAT-scoped read-only to a dedicated repo or a subfolder of this repo — this repo already has a GitHub remote: `allendefelixGHC/Creador-Contenido-Redes`), exposed on the `*.bacu5y.easypanel.host` wildcard via `domains.createDomain`. Keep the existing n8n pattern of raw `HTTP Request` nodes for PUT/GET/DELETE (same shape as today's Azure Blob calls) — do not introduce MinIO/S3 node wiring unless a future phase needs S3-ecosystem interop, because it adds an auth-model migration this phase doesn't need.

### Pattern 1: Mirror the existing REHOST-0X node shape, swap only the URL/auth, not the node type
**What:** The sub-workflow's 3 backend-touching nodes (`http-put-blob`, `build-blob-url`, and the ERR-01 `delete-azure-blob` node in the main workflow) currently build Azure-specific URLs from `$env.AZURE_STORAGE_ACCOUNT` / `$env.AZURE_CONTAINER` / `$env.AZURE_SAS_PARAMS`. The new pattern should introduce parallel env vars (e.g. `HOSTINGER_REHOST_BASE_URL`, `HOSTINGER_REHOST_API_KEY`) and swap the URL-building expressions and auth headers, while keeping the node type (`n8n-nodes-base.httpRequest`), the binary-passthrough discipline (`binary: $binary` in Code nodes, per the existing gotcha already documented in user memory), and the retry/onError wiring untouched.
**When to use:** For every node that currently talks to Azure Blob (`http-put-blob`, `build-blob-url`'s URL-construction, `http-head-verify`, `delete-azure-blob`, and `fb-fetch-ideogram-bytes`'s intra-cloud GET).
**Example (current Azure PUT, as the template to mirror):**
```json
// n8n/subworkflow-rehost-images.json, node "http-put-blob"
{
  "method": "PUT",
  "url": "=https://{{ $env.AZURE_STORAGE_ACCOUNT }}.blob.core.windows.net/{{ $env.AZURE_CONTAINER }}/{{ $json.blob_name }}?{{ $env.AZURE_SAS_PARAMS }}",
  "headerParameters": { "parameters": [
    { "name": "x-ms-blob-type", "value": "BlockBlob" },
    { "name": "Content-Type", "value": "={{ $json.content_type }}" }
  ]},
  "contentType": "binaryData", "inputDataFieldName": "data"
}
```
The Hostinger equivalent would be structurally identical, just: `url = "={{ $env.HOSTINGER_REHOST_BASE_URL }}/{{ $json.blob_name }}"`, header auth (e.g. `Authorization: Bearer {{ $env.HOSTINGER_REHOST_API_KEY }}` or a custom `X-Api-Key`) instead of SAS query params, and `x-ms-blob-type` dropped (Azure-specific).

### Pattern 2: One-seam hostname/URL rewrite in the aggregate node (REHOST-06 template)
**What:** Commit `9120db7` shows the exact shape — the aggregate `collect-blobs` Code node reads an env var and rewrites the URL before it's emitted as `blob_urls`, so every downstream Meta-facing consumer inherits the new URL transparently without being individually env-aware. For Hostinger, if the upload node (Pattern 1) already builds the final public URL directly (rather than a blob-storage-account URL needing a CDN rewrite), this seam may collapse into "no separate rewrite needed" — the URL built in `build-blob-url`/equivalent IS already the final Meta-reachable URL. This is a meaningful *simplification* opportunity vs. the AFD attempt (AFD needed a rewrite step because the origin URL and the CDN-fronted URL had different hostnames for the same object; Hostinger's service can just directly return its own public URL with no separate CDN layer in front).
**When to use:** Only if a genuine two-hostname situation persists (e.g. internal Docker network name vs. public wildcard domain differ) — otherwise, prefer building the final public URL once, at upload time, and skip the rewrite seam entirely.

### Pattern 4: ERR-01 cleanup — the `delete-azure-blob` node and its upstream `extract-blob-names`
**What:** `extract-blob-names` (line 3053) currently does a hardcoded string-prefix strip: `const prefix = 'https://propulsarcontent.blob.core.windows.net/posts/';` to recover the bare blob name from a full URL, before `delete-azure-blob` (line 3067) rebuilds an Azure DELETE URL with SAS params. Both need updating: the prefix must match whatever base URL the new Hostinger service publishes, and the DELETE call needs the new service's auth header (shared-secret) instead of SAS query params + `x-ms-*` headers.

### Anti-Patterns to Avoid
- **Don't reintroduce a CDN/rewrite hop unless genuinely needed.** The AFD attempt needed a rewrite because it was fronting an *existing* origin (Azure Blob) with a *different* edge hostname. A custom Hostinger app can just serve its own public URL directly — collapsing two hostnames into one removes a whole class of the AFD failure mode entirely (nothing to "reject" a fronting layer if there isn't one).
- **Don't put PII or client-identifiable data through this service.** Per `CLAUDE.md` global Azure rules, this is Propulsar's own marketing content (not client PII), so it's fine here, but this service is a new piece of shared infra — do not repurpose it later for client data without re-evaluating those rules.
- **Don't rely on `services.app.createService`'s `image` field alone** — per `deploy-vps-demo.md` and independently re-confirmed by the smoke test, that field does not persist; always follow with `services.app.updateSourceImage` (image path) or `services.app.updateSourceGit` + `services.app.updateBuild` (custom-build path), and always verify with `inspectService`/`inspectProject` afterward, never trust a bare `{}` response as proof of success.
- **Don't expose the VPS Postgres or unrelated internal services while building this** — irrelevant to this phase, but a documented gotcha for this exact EasyPanel instance (`services.postgres.exposeService` must be closed again immediately after use, N/A here since this phase needs no DB).

## Common Pitfalls

### Pitfall 1: Assuming a prebuilt Docker Hub image "obviously" supports upload/delete because it's a "file server"
**What goes wrong:** The smoke-test doc's own recommendation named `halverneus/static-file-server` as a candidate; it is read-only.
**Why it happens:** "File server" images are overwhelmingly read-serving tools (that's the far more common use case); write support is the exception, not the default, and is easy to assume without checking.
**How to avoid:** Verified in this research — do not use it. If evaluating any other prebuilt image, explicitly confirm PUT/upload AND DELETE support in its README before committing, don't infer from the image name/description.
**Warning signs:** A "file server" image whose documented env vars are all about serving/access-gating (`FOLDER`, `ACCESS_KEY`, `SHOW_LISTING`) with nothing about writes.

### Pitfall 2: `services.app.createService`'s `image`/`build.file` fields silently not persisting
**What goes wrong:** Calling `createService` with an `image` field, or `updateBuild` with a custom `file` name, appears to succeed (`200`, sometimes even echoes the field back) but the value never actually takes effect.
**Why it happens:** Confirmed and documented behavior of this specific EasyPanel instance/version — most `services.app.*` procedures don't validate or persist every field they accept.
**How to avoid:** Always follow creation with the dedicated setter (`updateSourceImage` or `updateSourceGit`+`updateBuild` with a literal `Dockerfile` filename), then re-fetch with `inspectService`/`inspectProject` to confirm.
**Warning signs:** A field you set doesn't show up (or shows the old/default value) on the very next `inspectService` call.

### Pitfall 3: `deployService` returning 500 with no useful reason, for one service while siblings deploy fine
**What goes wrong:** Confirmed to happen even when it's not a token/API/disk problem — happened previously with `control-plane-web` in this exact project.
**Why it happens:** Unclear root cause per the existing doc; sometimes resolved by hitting the per-service `deploymentUrl` webhook directly instead of the tRPC procedure, other times requires `hostShell` to run the build manually and read the real compiler/build error.
**How to avoid:** Don't assume infra failure — first retry via the `deploymentUrl` webhook (`services.app.inspectService` → `deploymentUrl` field), then fall back to `hostShell` manual build if that also silently does nothing.
**Warning signs:** Repeated `500`s from `deployService` on one service while other services in the same project deploy normally at the same time.

### Pitfall 4: Forgetting that the ERR-01 cleanup path parses blob names by hardcoded hostname/prefix string matching
**What goes wrong:** `extract-blob-names` (line 3053 of `n8n/workflow.json`) has `const prefix = 'https://propulsarcontent.blob.core.windows.net/posts/'` baked in as a literal string. If the rehost URL format from the new backend differs (different path structure, no `/posts/` segment, etc.) and this isn't updated in lockstep, the DELETE cleanup will silently fail to strip the prefix correctly and either delete nothing or throw on a malformed DELETE URL.
**Why it happens:** It's a plain string constant, not derived from an env var, so it's easy to miss when auditing "which nodes read AZURE_* env vars."
**How to avoid:** Explicitly grep for `propulsarcontent.blob.core.windows.net` (not just `$env.AZURE_`) across both workflow JSON files when doing the migration — this line will not show up in an env-var-only search.
**Warning signs:** DELETE cleanup calls silently no-op or 404 without anyone noticing (ERR-01's `onError: continueErrorOutput` will mask this — it fails open).

### Pitfall 5: SAS-stripping logic (`assert-fb-story-url`) becomes dead weight, not a bug, but worth simplifying
**What goes wrong:** Nothing breaks if left as-is — `assert-fb-story-url`'s SAS-param-stripping logic (`sig=`, `sv=`, `sp=`, etc.) will simply never trigger (`stripped` will always be `false`) once URLs come from Hostinger instead of Azure Blob, since Hostinger URLs won't carry SAS query strings.
**Why it happens:** The node was written specifically for Azure's SAS-in-URL auth model.
**How to avoid:** Not a required fix, but flag it in the plan as an optional cleanup — leaving it is harmless (fail-open no-op), removing it reduces confusion for future readers about why "Azure Blob"/"SAS" language still appears in notes after the backend has moved to Hostinger.
**Warning signs:** None (silent no-op) — this is a code-hygiene note, not a functional risk.

### Pitfall 6: Auth model mismatch between "public GET" and "authenticated PUT/DELETE" on the same service
**What goes wrong:** The GET endpoint (Meta's fetcher hits it) MUST be fully unauthenticated and public — Meta's `image_url` fetcher does not support sending custom headers or query-string signing the way n8n can when it calls PUT/DELETE itself. If the new service requires auth on GET too, Meta's fetch will 401/403 exactly like the AFD/Azure Blob failures, just for a different reason (auth, not hostname).
**Why it happens:** It's tempting to apply one uniform auth middleware to all routes for simplicity.
**How to avoid:** Explicitly split auth: GET routes public, PUT/DELETE routes gated behind a shared-secret header (something only n8n sends, via `$env.HOSTINGER_REHOST_API_KEY` in the `HTTP Request` node's header parameters — same pattern as today's `X-API-Key` header already used for YCloud calls in this same sub-workflow's `notify-abort` node).
**Warning signs:** Meta returns a 4xx/9004-style error on the *new* backend even though a manual `curl` to the same URL from a normal browser/dev machine works — check whether the service is enforcing auth on the GET path specifically.

## Open Questions

1. **Which language/framework for the custom upload/serve/delete service — Node/Express or Python/FastAPI?**
   - What we know: Either works equally well with EasyPanel's git+Dockerfile deploy flow; `propulsar-atiende` already has a proven Python+uv+Dockerfile pattern working on this exact VPS/EasyPanel instance; this repo (`CreadorContenido`) itself is Node-based (the Wizard is `wizard/run.js`).
   - What's unclear: No hard requirement favors one over the other — this is a coin-flip stylistic choice, not a technical constraint.
   - Recommendation: Planner's discretion; either is a ~100-line service. If reusing/adapting `propulsar-atiende`'s existing Dockerfile/build boilerplate saves setup time, Python is slightly less net-new; if keeping the whole re-host concern in this repo's own idiom (Node), Express is more consistent with `CreadorContenido`'s existing stack. Not worth extensive deliberation.

2. **Exact repo location for the new service's source (for `updateSourceGit`'s PAT scope).**
   - What we know: This repo has a working GitHub remote (`allendefelixGHC/Creador-Contenido-Redes`); `propulsar-atiende`'s PAT is scoped narrowly to that one repo per its own docs ("solo lectura, acotado a `propulsar-ai/propulsar-atiende`").
   - What's unclear: Whether it's preferable to add a `rehost-service/` subfolder to *this* repo (simplest, no new repo to manage, but this repo's PAT scope would need to be a fresh fine-grained token specific to `Creador-Contenido-Redes`) vs. a small brand-new dedicated repo (cleaner separation, since this is arguably shared Propulsar infra rather than Content-Engine-specific).
   - Recommendation: Default to a subfolder of this repo unless the planner/user has a reason to keep it as standalone shared infra (e.g. if other future Propulsar projects might also want to re-host images this way) — simplicity tiebreaker per `CLAUDE.md`.

3. **Exact env var and Key Vault secret naming for the new backend.**
   - What we know: Existing convention on this Container App is flat, descriptive names (`AZURE_STORAGE_ACCOUNT`, `AZURE_CONTAINER`, `AZURE_SAS_PARAMS` as a Key-Vault-backed secretRef, `AZURE_CDN_HOST` as a plain value) set via `az containerapp update --set-env-vars` / `az containerapp secret set` + Key Vault.
   - What's unclear: Nothing technically — this is purely a naming decision, e.g. `HOSTINGER_REHOST_BASE_URL` (plain, e.g. `https://rehost-propulsar-atiende-demo.bacu5y.easypanel.host`) + `HOSTINGER_REHOST_API_KEY` (Key-Vault-backed secretRef, analogous to `azure-sas-params`).
   - Recommendation: Follow the exact existing naming/secret-storage convention (Key Vault `propulsar-prod-kv`, secret name `hostinger-rehost-api-key`, Container App secretRef of the same name) — no new pattern needed.

4. **Whether to keep the old Azure Blob PUT/GET/DELETE nodes as a documented fallback path, or fully remove them.**
   - What we know: `12.1-02` precedent kept the AFD rewrite as an *additive, env-gated* seam ("Safe fallback: when env var unset, degrades to pre-12.1 behavior") rather than deleting the old path outright.
   - What's unclear: Whether that additive-fallback discipline is worth repeating here, given AFD's fallback ended up being "fall back to a band-aid that's also being replaced" (not a clean rollback target) — versus this phase's fallback target (Options D/B/E, i.e. `final_image_url`) is a real, already-proven-working state.
   - Recommendation: Given the AFD rollback precedent (`3b09fd6`/`505b52f` — a clean `git revert` of the exact commits, not a runtime env-var toggle) worked well and fast (~10-15 min per `12.1-02` decisions), plan for the same discipline here: implement as a clean, revertible commit sequence rather than an env-gated dual-path in the workflow JSON itself. Simpler to reason about, and git revert already has a proven track record on this exact seam.
