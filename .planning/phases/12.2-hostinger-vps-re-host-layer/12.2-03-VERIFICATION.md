## Why a harness workflow (method note)

n8n's public REST API has no endpoint to directly execute an arbitrary workflow: `POST /api/v1/workflows/{id}/run` returned `405 {"message":"POST method not allowed"}` when tested live against `https://n8n-azure.propulsar.ai` before writing any test code.

The sub-workflow (`BIaG266Q6AZpv4Sq`, "Re-host Images to Azure Blob") starts with an `n8n-nodes-base.executeWorkflowTrigger` node, which can only be entered via another workflow's "Execute Workflow" node — never directly via webhook or API.

Firing a real brief through the production `WEBHOOK_URL` (the "minimal main-workflow test path" alternative the plan also allows) was rejected after inspecting the live main workflow: the re-host sub-workflow call (`🔁 Re-host Images`) happens **after** WhatsApp SI approval, not before — confirmed by reading `🔧 Prep Re-host Input`'s live jsCode, which derives `post_id` from `data.session_id` (set by the Supabase session-recovery step that only runs on the approval-webhook path). `🔗 Merge Rehost Output` connects directly into the format-branch that leads straight into the 5 Meta-facing container-creation nodes with no safe stopping point in between — approving via WhatsApp would risk firing real Meta calls mid-test, which this plan's Task 1 explicitly forbids.

**Resolution:** a small, disposable harness workflow was created via the n8n API:
`Webhook (POST) -> Flatten Body (Code) -> Execute Workflow -> BIaG266Q6AZpv4Sq`, with `responseMode: lastNode` so the HTTP response IS the sub-workflow's real output. This calls the exact, already-deployed, unmodified sub-workflow object production uses — nothing about the sub-workflow itself was faked or mocked. The harness was deleted at the end of this plan (see Cleanup).
