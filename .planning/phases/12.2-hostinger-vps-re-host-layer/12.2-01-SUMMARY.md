## Decisions Made
- **Repo is public — no GitHub PAT needed.** The plan assumed a fine-grained, read-only PAT would need to be created (a genuine human-UI-only step). Discovered mid-execution that `Creador-Contenido-Redes` moved to the `propulsar-ai` GitHub org and is **public**, so `services.app.updateSourceGit` just uses the plain `https://github.com/propulsar-ai/Creador-Contenido-Redes.git` URL with zero embedded credentials — eliminates both the manual-PAT-creation step and the security exposure of embedding any token in EasyPanel's stored config for this service.
- **EasyPanel API requires POST everywhere**, contradicting `deploy-vps-demo.md`'s GET annotations for `listProjects`/`inspectProject`/`inspectService` (405 on GET, works on POST with a JSON body). Worth a doc fix in a future session.
- **Mount persistence achieved via hostShell, not the tRPC API** — confirmed this VPS runs Docker Swarm (`docker service ls`); `docker service update --mount-add type=bind,source=...,target=/data <service>` is the real, working mechanism. Verified live: PUT → GET byte-identical with the mount attached.
- **Escalating, not silently accepting, the mount-durability gap**: `services.app.restartService` regenerates the container's mount spec from EasyPanel's own stored config (which never learns about our manually-added mount) and drops it — proven live (PUT → restart → GET 404 → host file still present on disk → reapply mount → GET 200 again). Host data is never destroyed, but the running container temporarily disconnects from it on any EasyPanel-triggered restart/redeploy of this specific service. No EasyPanel-native fix found after ~50 candidate procedure names tried. Flagged directly to the user (see below) and in `12.2-01-SMOKE.md`, per the plan's explicit instruction to escalate rather than bury this in a doc.

## Escalation: rehost-service mount durability gap

`rehost-service`'s uploaded files are stored on the VPS host at `/etc/easypanel/projects/propulsar-atiende-demo/rehost-service/data` via a Docker Swarm bind mount that I attached manually through EasyPanel's `hostShell` WebSocket (no EasyPanel tRPC API exposes this for app-type services — extensively verified, ~50 candidate procedure names tried).

**The gap:** any future `restartService` or `deployService` call against this specific service (through EasyPanel's normal panel/API — e.g. a routine env-var change, or a future code redeploy) will silently drop that mount from the running container. The host-side files are never deleted, but the container temporarily can't see them, so every existing image would 404 (including anything in flight for a scheduled Meta post) until someone manually re-runs:
```bash
docker service update --force --mount-add type=bind,source=/etc/easypanel/projects/propulsar-atiende-demo/rehost-service/data,target=/data propulsar-atiende-demo_rehost-service
```
via the hostShell WebSocket, exactly as done in this plan.

Two realistic paths forward, your call:
1. **Accept it as a documented runbook step** — cheap today, but easy to forget on a future redeploy, and the failure mode (silent 404s) is easy to miss until a real post fails.
2. **Investigate further in a follow-up session** using EasyPanel's actual web UI (its "Mounts" tab, if this version has one) — this needs the panel's email/password login, which isn't currently stored anywhere I have access to (only the API token). If you have it, that's the fastest way to find the real underlying API call.

I did not pick an option — flagging it here per the plan's explicit instruction, since it changes this phase's actual durability guarantee.
