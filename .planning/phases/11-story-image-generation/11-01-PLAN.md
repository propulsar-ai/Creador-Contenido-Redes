**Goal:** Confirm the `content_sessions` table accepts `format='story'` + `story_expires_at` (TIMESTAMPTZ) + `aspect_ratio` (TEXT) inserts before Plan-01 Task 2 wires a production node that depends on them. **This task does NOT edit `n8n/workflow.json`.** It is a DB-side diagnostic + conditional migration. It is listed first because T2/T3 depend on the schema being correct. The commit at the end of this task records the probe result and any ALTER TABLE run, so reviewers can trace the schema evolution.

### Steps

1. Load `.env` and read `SUPABASE_URL` and `SUPABASE_ANON_KEY`:
   ```bash
   export $(grep -E '^(SUPABASE_URL|SUPABASE_ANON_KEY)=' .env | xargs)
   ```

2. Dry-run INSERT a probe row. Use a deterministic `session_id` (`probe_phase11_YYYYMMDDHHMM`) so it's trivially identified and deleted:
   ```bash
   PROBE_ID="probe_phase11_$(date -u +%Y%m%d%H%M)"
   curl -sS -w "\nHTTP_STATUS:%{http_code}\n" -X POST \
     "$SUPABASE_URL/rest/v1/content_sessions" \
     -H "apikey: $SUPABASE_ANON_KEY" \
     -H "Authorization: Bearer $SUPABASE_ANON_KEY" \
     -H "Content-Type: application/json" \
     -H "Prefer: return=representation" \
     -d "{
       \"session_id\": \"$PROBE_ID\",
       \"approval_number\": \"34600000000\",
       \"topic\": \"phase11 schema probe\",
       \"type\": \"educational\",
       \"platforms\": [\"instagram\"],
       \"status\": \"pending\",
       \"format\": \"story\",
       \"aspect_ratio\": \"9:16\",
       \"story_expires_at\": \"2026-04-21T12:00:00Z\",
       \"publish_at\": \"now\"
     }"
   ```

3. Interpret the response:
   - **201 Created** → schema already supports all 3 fields. Delete the probe row (next step) and proceed to Task 2.
   - **400 Bad Request** with body mentioning `story_expires_at` → run the migration below for that column only.
   - **400 Bad Request** with body mentioning `aspect_ratio` → run the migration below for that column only.
   - **400 Bad Request** with body mentioning `format` → STOP — something's wrong with Phase 7's work; flag before proceeding.

4. **If migration needed (400 response):** Surface the exact missing-column error to the user via a `checkpoint:human-action` style pause. Print this block verbatim and halt:
   ```
   ⚠ Supabase schema migration required for Phase 11.
   Missing column(s): <list from 400 body>

   Run this SQL in Supabase SQL Editor (app.supabase.com → SQL Editor):

   -- Run only the lines for columns the 400 flagged as missing:
   ALTER TABLE content_sessions ADD COLUMN IF NOT EXISTS story_expires_at TIMESTAMPTZ;
   ALTER TABLE content_sessions ADD COLUMN IF NOT EXISTS aspect_ratio TEXT;

   Then reply "migrated" so Task 1 can re-probe and confirm.
   ```
   After the user replies "migrated", re-run the probe from step 2. Expect 201.

5. **Delete the probe row** so we don't pollute the table:
   ```bash
   curl -sS -X DELETE \
     "$SUPABASE_URL/rest/v1/content_sessions?session_id=eq.$PROBE_ID" \
     -H "apikey: $SUPABASE_ANON_KEY" \
     -H "Authorization: Bearer $SUPABASE_ANON_KEY"
   ```
   Verify empty response body (204). If 404 or other, log it but proceed — the row could be gone already.

6. **Record the probe result in the commit message** (this task does NOT modify files, but we still commit to keep the schema-probe audit trail):
   - If no migration was needed: `chore(11-01): probe Supabase — story_expires_at + aspect_ratio columns exist (no DDL run)`
   - If migration was run: `chore(11-01): probe Supabase — ALTER TABLE added story_expires_at + aspect_ratio`

**DO NOT proceed to Task 2 until the probe returns 201 and the probe row is deleted.**

### Why the probe row and not an introspection query
PostgREST doesn't expose a JSON endpoint for table column lists without custom RPC. A POST-then-delete is the canonical pattern (Phase 7 used the same approach when adding `format` and `image_urls`). The write path is idempotent because we delete immediately.
